# آزمون‌های پیش از انتشار 6.26.0-meta.1

## نتیجهٔ اصلی

هر ۹ اجرای کامل `rx/0` با checksum رسمی درست تمام شدند. VAES512 روی CPU میزبان واقعاً انتخاب شد. **افزایش قابل‌اتکای هشریت کامل اثبات نشد.** در این سری، میانهٔ VAES512 از baseline پایین‌تر بود؛ پراکندگی اجراها نیز زیاد است. بنابراین این نسخه برای آزمایش روی سیستم هدف منتشر می‌شود و انتخاب پیش‌فرض `auto` باقی می‌ماند.

## محیط ساخت و آزمون

- تاریخ: ۲۰۲۶-۱۰-۰۵؛ زمان‌های داخل لاگ با منطقهٔ زمانی محلی چاپ می‌شوند و `created_utc` در JSON بر مبنای UTC است.
- CPU این مرحله: ماشین مجازی `Intel Xeon Platinum 8573C`، ۹ vCPU قابل‌دسترسی، سهم CPU معادل ۸ هسته و محدودیت RAM برابر ۸ GiB.
- سیستم: Ubuntu 24.04 / Linux x86-64؛ GCC 13.3.0؛ libuv 1.48.0؛ OpenSSL 3.0.13؛ hwloc 2.12.1.
- دو executable استاتیک با گزینه‌های یکسان، backend CPU، JIT و hardware AES فعال؛ VAES512 در واحد کامپایل جداگانه.
- الگوریتم `rx/0`، ۸ ترد، در هر اجرا ۲۵۰ هزار هش؛ ۳ دور برای هر انتخاب، با چرخش ترتیب اجرا.
- huge pages و نوشتن MSR خاموش؛ prefetch برابر ۱؛ yield روشن؛ NUMA روشن؛ init با ۸ ترد. تنظیم دقیق هر اجرا از JSON مستقل اعمال شد.
- baseline از commit اصلی `b2ca72480c58d197e18c885d9fc1a0c8d517e60a` ساخته شد. باینری Release مجدداً از سورس tag روی runner Ubuntu 22.04 ساخته و قبل از انتشار checksum آن بررسی می‌شود؛ مشخصات دقیق آن داخل `BUILD_INFO.txt` خواهد بود.

این محیط با مرحلهٔ اولیهٔ بررسی که روی AMD EPYC 9V74 انجام شده بود متفاوت است. نتیجهٔ microbenchmark قبلی را نباید به CPU این مرحله یا سیستم کاربر تعمیم داد.

## صحت کامل rx/0 و عددهای مشاهده‌شده

checksum مورد انتظار چندترد برای ۲۵۰ هزار هش: `7D6054757BB08A63`. هر ۹ اجرا دقیقاً همین مقدار را تولید کردند.

| نسخه / مسیر | H/s در سه اجرا | میانهٔ H/s | کمینه تا بیشینه | اختلاف میانه با baseline |
|---|---|---:|---|---:|
| XMRig اصلی | 1803.0، 1445.9، 1723.7 | 1723.7 | 1445.9 تا 1803.0 | 0% |
| MetaXMRig / aes | 1910.1، 1597.6، 1922.9 | 1910.1 | 1597.6 تا 1922.9 | +10.81% |
| MetaXMRig / vaes512 | 1952.9، 1502.7، 1625.1 | 1625.1 | 1502.7 تا 1952.9 | −5.72% |

این جدول مشاهدات خام است، نه برآورد قطعی اثر تغییر کد. بازه‌ها به‌شدت هم‌پوشانی دارند، میزبان مجازی تحت نوسان منابع قرار دارد و در بخشی از سری، ساخت و آزمون تنظیمات نیز انجام شد. کرنل استاندارد AES بازنویسی نشده است؛ عدد +10.81% را نمی‌توان به‌عنوان بهینه‌سازی اثبات‌شده معرفی کرد. عدد منفی VAES512 هم ثابت نمی‌کند که روی همهٔ CPUها کندتر است. برای مقایسهٔ قابل‌اتکا باید روی سیستم هدفِ بدون بار هم‌زمان و با شرایط ثابت تکرار شود.

نتیجهٔ خام: [v6.26.0-meta.1-rx0.json](results/v6.26.0-meta.1-rx0.json). در لاگ‌ها برای سه اجرای VAES512، انتخاب `AES implementation: vaes512` ثبت شد. در ورودی‌های معمول worker، scratchpad و stateها هم‌ترازی لازم را دارند.

## صحت مسیر rx/2

یک اجرای اضافی با باینری نهایی، `rx/2`، مسیر VAES512، ۸ ترد و ۲۵۰ هزار هش انجام شد. checksum برابر `18CF741A71484072` بود و با مرجع رسمی چندترد تطابق داشت. مسیر انتخاب‌شده `vaes512`، زمان هش‌زدن ۱۵۷٫۵۸۷ ثانیه و نرخ مشاهده‌شده ۱۵۸۶٫۴ H/s بود. این یک آزمون صحت است؛ مقایسهٔ کارایی تکراری برای rx/2 انجام نشده است.

نتیجهٔ خام: [v6.26.0-meta.1-rx2.json](results/v6.26.0-meta.1-rx2.json).

## آزمون دقیق کرنل AES

اسکریپت `scripts/test_aes.sh` روی CPU واجد قابلیت با موفقیت اجرا شد. در ۱۲۸ ورودی مستقل، سه بخش دقیقاً مقایسه شدند: خروجی hash ۶۴ بایتی، fill state ۶۴ بایتی و تمام scratchpad دو مگابایتیِ به‌روزشده. همهٔ مقایسه‌ها موفق بودند.

تایمینگ این اجرای تأیید صحت با کارهای دیگر هم‌زمان بود و برای ادعای سرعت استفاده نمی‌شود. آزمایش جداگانهٔ مرحلهٔ قبلی روی AMD، حدود ۱۰٫۶۱٪ افزایش throughput همین تابع نشان داده بود؛ آن عدد، هشریت کامل ماینر نیست.

## آزمون تنظیمات و CLI

`tests/test_aes_config.py` باینری نهایی را با API محلی و یک اتصال محلی بدون job اجرا کرد. در سه حالت زیر، JSON خروجی برنامه بررسی شد:

| حالت | AES ذخیره‌شده در خروجی | نتیجه |
|---|---|---|
| config با `aes`، بدون override | `aes` | موفق |
| همان config با `--randomx-aes=vaes512` | `vaes512` | موفق |
| همان config با مقدار CLI نامعتبر | `auto` | موفق |

در هر سه حالت، مقادیر `mode`، `init`، `init-avx2`، `wrmsr`، `rdmsr`، `numa`، `1gb-pages` و `scratchpad_prefetch_mode` حفظ شدند. `cpu.enabled` و `cpu.hw-aes` نیز خاموش باقی ماندند. این آزمون تأیید می‌کند که گزینهٔ جدید CLI آبجکت RandomX کاربر را جایگزین نمی‌کند. هیچ job، هش یا share استخر در این آزمون تنظیمات اجرا نشد.

`--help` گزینهٔ جدید را نمایش داد و `--version` نام MetaXMRig و نسخهٔ `6.26.0-meta.1` را برگرداند. ساخت Release، بررسی استاتیک‌بودن executable، بررسی syntax اسکریپت‌های shell و `git diff --check` موفق بودند.

در اولین اجرای CI روی Ubuntu 22.04، FindUV upstream فایل shared را انتخاب کرد و لینک استاتیک شکست خورد. اسکریپت ساخت اصلاح شد تا هر دو نام `libuv.a` و `libuv_a.a` را پشتیبانی کند و مسیر فایل استاتیک را صریحاً به CMake بدهد. این اصلاح بسته‌بندی است و کد هش‌زدن را تغییر نمی‌دهد.

## مرز نتیجه‌ها

آزمون share پذیرفته‌شدهٔ استخر، CPU بدون AVX-512، Zen 5، تک‌ترد، سایر سیستم‌عامل‌ها و اندازهٔ 1M در این مرحله اجرا نشده‌اند. pipeline Release فایل‌های اجرایی واقعی را دوباره می‌سازد و checksum آفلاین آن‌ها را قبل از انتشار بررسی می‌کند. فایل `results.json` و آرشیو `ci-verification.tar.gz` در Release به همین آزمونِ runner مربوط‌اند؛ اجرای VAES512 یا fallback از فیلد `selected_aes` مشخص است.

برای نصب، بازتولید و ارسال نتیجهٔ سیستم خودت، [TESTING_FA.md](TESTING_FA.md) را ببین. اگر VAES512 روی سیستم تو نتیجهٔ بهتری نداشت، `aes` یا `auto` را انتخاب کن.
